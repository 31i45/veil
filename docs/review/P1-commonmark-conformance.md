# P1 CommonMark 一致性评审

> 评审日期：2026-10-26
> 评审对象：Veil 工作树（阶段 C 完成，573 测试全绿）
> 语料：CommonMark 0.31.2 官方规范示例 **652 例**
> 配套产物：[P0 功能对标评审](P0-feature-parity.md)
> 性质：**解析与导出一致性**。不覆盖 GFM 扩展、渲染/布局、编辑操作往返、性能与稳定性长跑（那是 P2/P3）

## 1. 结论摘要

### 1.1 总表

| 指标 | 结果 | 通过率 |
|---|---|---|
| 语料规模 / 崩溃 | 652 例 / **0 panic** | — |
| A. 自有块解析器：顶层块序列 | 431 / 652 | **66.1%** |
| B. 产品导出路径：HTML 逐字节精确 | 489 / 652 | **75.0%** |
| B. 产品导出路径：HTML 规范化后 | 490 / 652 | **75.2%** |
| C. 自有行内解析器：行内节点计数 | 451 / 652 | **69.2%** |

### 1.2 条件指标（只在 A 通过时统计）

| 条件指标 | 结果 | 通过率 |
|---|---|---|
| A 通过时，B 精确 | 410 / 431 | **95.1%** |
| A 通过时，B 规范化 | 411 / 431 | **95.4%** |
| A 通过时，C 行内计数 | 323 / 431 | **74.9%** |

### 1.3 四条结论

1. **主缺陷在块解析，不在导出器。** A 通过时导出精确率 95.1%，说明只要块分段正确，导出链路本身很稳。
2. **B 的 75.0% 不能当作 Veil 的兼容性对外宣传。** 产品导出把每个块（或连续列表项）的源码再次交给 pulldown-cmark 解析；652 例中有 **79 例 A 失败但 B 精确通过**，是 pulldown 重新识别源码把 Veil 的块模型错误掩盖了。HTML 块一节最典型：A 3/44，B 34/44。
3. **行内解析是第二瓶颈。** 即使块结构全对，行内计数仍有 108 例失败（条件通过率 74.9%），集中在强调、引用式链接、图片、自动链接。
4. **稳定性正面。** 652 例在 `Session::open → blocks → export → inline` 全链路无 panic；但这不代表渲染与编辑器交互无崩溃。

一句话：**Veil 的块解析器是 v0 子集，导出器替它遮住了大部分错误。**

## 2. 方法与判定

### 2.1 语料

- 来源：CommonMark 0.31.2 官方规范 `commonmark-spec.json`（652 例）。
- 每个示例拆为 `NNNN.md` + `NNNN.html`，索引含节名，共 26 节。
- 语料原文未做任何改写；`.md` 原样输入，`.html` 作为期望值。
- 语料目录（临时，不入库）：`C:\Users\31i45\AppData\Local\Temp\veil-review\examples`。

### 2.2 三套判定

| Suite | 被测对象 | 判定方式 | 回答的问题 |
|---|---|---|---|
| **A** | Veil 自有块解析器 | 顶层块序列 vs 规范 HTML 的顶层块标签序列 | 块模型是否正确 |
| **B** | 产品导出路径 | 复刻导出分段后调用 pulldown-cmark 0.13，HTML 与规范逐字节比较 | 用户导出的结果是否正确 |
| **C** | Veil 自有行内解析器 | `strong/em/code/link/image/del` 节点计数 vs 规范 HTML 标签计数 | 行内模型是否识别正确 |

实现细节：

- A 的期望序列由轻量 HTML 标签扫描得到（容器级，只取顶层；连续列表项折叠为一个 `List`）。
- B 严格复刻产品导出：连续 `ListItem` 合并为一段源码，`Math` 跳过，其余块逐个调用 `html::push_html`；与产品一致启用 tables/strikethrough/tasklists 选项。
- C 只比较数量，不比较文本内容、嵌套顺序与 URL。
- 规范化：`<pre>` 外折叠空白、丢弃标签间空白；`<pre>` 内原样保留。

### 2.3 为什么给出条件指标

C 直接对 652 例统计会被块结构错误污染：块切错后，行内节点数量自然对不上，不能归因于行内解析器。因此同时给出「仅 A 通过」的条件通过率，用于分离两类缺陷。

### 2.4 复现

```powershell
$env:CARGO_TARGET_DIR="$env:TEMP\veil-review\target"
cargo run --release --manifest-path "$env:TEMP\veil-review\harness\Cargo.toml" -- "$env:TEMP\veil-review\examples"
```

harness 依赖：`veil-core`（path 指向本仓库）+ `pulldown-cmark 0.13`（`features = ["html"]`，与产品同版本）。原始结果落盘于 `$env:TEMP\veil-review\conformance-result.txt`。

### 2.5 工具边界（必须与数字一起读）

1. **A 是代理指标，不是字节级判定。** 期望序列由 HTML 扫描启发式得到；例如 `#0021` 的规范期望 HTML 是裸行内标签 `<a href="/bar\/)">`，扫描得到空序列，会把正确的段落判为失败。此类**工具误判**应剔除，不能算产品缺陷。
2. **B 复用 pulldown-cmark，不能证明自有解析器正确。** 它测的是「Veil 的块分段 + pulldown 的解析」的合成结果；B 高通过率中有相当部分属于 pulldown 的功劳。
3. **C 是弱判定。** 数量相等不代表结构正确（可能一错一错相互抵消）；数量不等则一定有问题。C 通过率应视为**上限**。
4. **仅 CommonMark。** 表格、任务列表、删除线虽已实现，但不在本语料内，未测。
5. **不覆盖编辑器行为。** 语法高亮、折叠、光标展开、IME、撤销、保存往返均未纳入。

## 4. 失败分类与根因

以下类别按「A 失败例数」排序；类别间有重叠（例如引用式链接同时计入 Links 与 Link refs），不求和。

### 4.1 HTML 块：41 例 A 失败（A 3/44，B 34/44）

规范期望 `<div>/<table>/<script>/<style>` 等作为独立 HTML 块；Veil 无 HTML 块分支，整段当段落。导出时 pulldown 重新扫描源码，仍输出正确 HTML，因此 B 高。

- 影响：导出结果尚可，但**编辑器内块语义错误**（大纲、折叠、块级操作把 HTML 当正文段落）。
- 代码位置：[block.rs](../../crates/veil-core/src/syntax/block.rs) `scan_one` 无 HTML 块分支。

### 4.2 Links：40 例 A 失败（A 50/90，B 55/90）+ Link refs 18 例（A 9/27）

`#0023` 输入：

```markdown
[foo]

[foo]: /bar\* "ti\*tle"
```

规范输出 `<p><a href="/bar*" title="ti*tle">foo</a></p>`；Veil 输出两个段落。

根因：[inline.rs](../../crates/veil-core/src/syntax/inline.rs) 只实现 `[text](url)`（URL 扫到首个 `)`，不支持 title），**无引用定义、无 label 匹配、无引用式链接/图片**。在真实文档中，引用式写法是长文最常见的链接形式之一。

### 4.3 Setext 标题：17 例 A 失败（A 10/27，B 13/27）

`#0080` 输入：

```markdown
Foo *bar*
=========

Foo *bar*
---------
```

规范：`h1` + `h2`；Veil：`P P Rule`。

根因：已知取舍，[block.rs](../../crates/veil-core/src/syntax/block.rs#L62) 明确注释「setext 标题 v0 不支持，按分隔线处理」。`===` 不被识别，`---` 被当分隔线。这是纯块解析问题，修复面局部。

### 4.4 列表项/列表：26 + 15 例 A 失败（List items 22/48，Lists 11/26）

`#0004` 输入：

```markdown
  - foo

	bar
```

规范：一个列表项，内含两个段落；Veil：`List P`，续段逃出列表。

根因：列表项按单行建模（[block.rs](../../crates/veil-core/src/syntax/block.rs#L202) `list_mark`），缺「续行缩进 ≥ 内容起始列」与宽松列表（项间空行、项内多段）的归属规则，也缺引用块的懒续行。这不仅是语法边角，**真实文档的列表几乎都是多段/多行**。

### 4.5 围栏代码块：12 例 A 失败（A 17/29，B 23/29）

失败集中在缩进围栏、容器（引用/列表）内围栏与闭合边界。Veil 的围栏吞咽能处理基础情形，但容器内缩进换算与「闭合围栏可短于开启围栏」等边界未覆盖。

### 4.6 缩进代码块：10 例 A 失败（A 2/12，B 7/12）

`#0069` 输入 `    # foo`，规范为 `<pre><code># foo`；Veil 识别为 H1。
`#0048` 输入 `    ***`，规范为代码块；Veil 识别为分隔线。

根因：无「4 空格缩进即代码块」规则，缩进后的标题/分隔线仍按去缩进文本匹配。[block.rs](../../crates/veil-core/src/syntax/block.rs#L118) 的标题识别会先 `trim_start`。

### 4.7 引用块懒续行：7 例 A 失败（Block quotes 18/25）

`#0093` 输入：

```markdown
> foo
bar
===
```

规范：整个三行是一个引用块内的段落；Veil：`Quote P`，引用在 `bar` 处终止，同时叠加 Setext 缺失。根因：[block.rs](../../crates/veil-core/src/syntax/block.rs#L270) `quote_lines` 只按 `>` 标记行收集，未实现懒续行。

### 4.8 强调：行内 63 例失败（A 131/132，C 69/132）

块级几乎全对，行内识别大面积偏离。根因：[inline.rs](../../crates/veil-core/src/syntax/inline.rs#L3) 明确采用「最左匹配」简化算法，无 CommonMark 的 delimiter run、左右 flanking、rule of 3。典型后果：

- `- Foo` / `- * * *`（`#0061`）：分隔线在列表项内被识别出 1 个多余 `emph`。
- 多段/嵌套强调：可能过度识别或漏识别（C 计数双向都有失败）。

这是**风险最高**的修复项：改动集中在行内扫描内核，容易引入回归，必须先补规范语料门禁再改。

### 4.9 自动链接：行内 11 例失败（A/B 19/19，C 8/19）

`<https://example.com>` 在规范中应生成链接；Veil 自有解析器当纯文本。导出 HTML 却正确，因为 pulldown 重新解析了源码——**这是「导出正常不代表编辑器正常」的最清晰证据**。

### 4.10 图片：14 例 A 失败（A 8/22）

大量样例使用引用式定义、title、尖括号 URL；v0 仅支持 `![alt](url)`。产品侧还叠加「仅 PNG 解码」的限制（P0）。

### 4.11 实体、反斜杠与 Tabs：3 + 4 + 6 例 A 失败

- 实体：部分命名实体/数字引用未解码（A 14/17，C 14/17）。
- 反斜杠：可转义字符集为 v0 白名单，且受块缩进误判牵连（A 9/13）。
- Tabs：制表位展开不完整，缩进语义随块类型漂移（A 5/11，B 9/11）。

### 4.12 小项

- Code spans：21/22 块级，C 16/22（反引号串长度/首尾空格规则）。
- Hard line breaks：13/15（反斜杠与两空格换行在部分容器内失效）。
- Thematic breaks：16/19，失败主要来自缩进误判（`    ***` 应为代码）。
- ATX：16/18，失败来自缩进代码误判（`    # foo`）。

## 5. 对产品的含义

1. **「CommonMark 兼容」目前不成立。** 真实文档一旦出现 Setext、缩进代码、引用式链接、宽松列表，Veil 的块模型就会给出与主流渲染器不同的结果；这不是罕见边角。
2. **「HTML 导出 75%」是合成指标，不能对外。** 导出器通过 pulldown 二次解析掩盖自有块模型缺陷；应把 A（66.1%）作为解析能力的对外口径，且需先剔除 A 的工具误判。
3. **编辑器内的正确性比导出更重要。** 用户日常看到的是 Veil 的块/行内模型；Autolinks、Emphasis、Links 的导出正确但编辑器错误，会直接表现为「预览/大纲/光标展开不对」。
4. **这不是「再加几个语法」的问题。** 列表多段、懒续行、容器内缩进属于块模型结构，不是分支补丁；需要一次有边界的块模型升级（对应阶段 D 的语料门禁先行）。
5. **CJK 与资源数据是相对优势。** 本语料不评价中文排版与性能；结合 P0，Veil 的差异化仍在「源码真值 + 低延迟 + CJK/IME」，而不是规范覆盖数量。

## 6. 修复优先级（建议）

| 优先级 | 项 | 依据 | 风险 |
|---|---|---|---|
| P0 | 引用定义 + 引用式链接/图片 | Links 40、Link refs 18、Images 14 例 A 失败；真实文档高频 | 中（需新增文档级符号表） |
| P0 | Setext 标题 | 17 例 A 失败；修复局部 | 低 |
| P0 | 宽松/多段列表项 + 懒续行 | List items 26、Lists 15、Block quotes 7；真实文档高频 | 高（块模型结构调整） |
| P1 | 缩进代码块 | 10 例 A 失败；与现有缩进处理冲突 | 中 |
| P1 | 围栏代码边界（容器/缩进/闭合） | 12 例 A 失败 | 低 |
| P1 | 行内强调算法（delimiter run/flanking） | C 63 例失败 | 高（回归风险，需先建门禁） |
| P1 | 自动链接 | C 11 例失败；实现简单 | 低 |
| P2 | HTML 块 | A 41 例失败，但导出已正确（B 34/44）；收益主要在编辑器 | 中 |
| P2 | 实体/反斜杠/Tabs/行内代码细节 | 合计约 13 例 A 失败 | 低 |

前置条件：**先把这个 harness 固化为 dev-only 一致性测试（阶段 D3）**，再动解析器；否则无法证明「修一处、不坏其他」。GFM（表格、任务列表、删除线）需要独立语料，不能复用本报告数字。

## 7. 判定

- **解析能力**：CommonMark 0.31.2 块级 66.1%、行内（条件）74.9%，属于**明确未达标**。
- **导出能力**：在块分段正确的条件下 95.1% 精确，链路本身可用；但 75.0% 的整体数字被 pulldown 二次解析美化，不能作为兼容性结论。
- **稳定性**：652 例 0 panic，属于**正面但有限**的结论（不含渲染与交互）。
- **可行动结论**：P0 修复引用式链接、Setext、宽松列表；P1 修行内强调与自动链接；HTML 块可延后。修复前先落地一致性门禁。
