# 延后项与人工验证登记（2026-11-27）

> 依据：`docs/qa/perfect-surface-audit-2026-11-27.md`（F 台账）与 `.trae/specs/converge-perfect-writing-surface/spec.md` 的「证据闭合与延后登记」需求。
> 本文只做两件事：把**确实需要人在场或硬件**的验证项写成可复现步骤与判定标准；把**本轮明确不做**的能力写成「为什么现在不做 + 何时重开」。
> 约定：未执行的项一律写 **NOT RUN**，不写成「预期通过」。

## 1. 人工验证项（需人在场 / 需硬件）

自动化能覆盖的部分已由测试固定；以下项因涉及系统设置、物理设备或真人输入法交互，本轮不伪造结果。

### 1.1 系统 DPI 100% / 125% / 150% / 200%

- 状态：**NOT RUN**（150% 仅有自动首帧检查，见 `docs/review/jobs-lens-report-v2.md:270`；100/125/200 未实测）
- 为什么不能自动化：DPI 是 Windows 显示设置的系统级状态，切换会改变所有进程的物理像素映射，通常需要注销/重启，且会干扰同一台机器上的其它工作；headless 测试只能改逻辑缩放因子，不能证明系统 DPI 切换后的真实首帧、命中与版心。
- 可复现步骤：
  1. Windows 设置 → 系统 → 屏幕 → 缩放，依次设为 100%、125%、150%、200%（每次改完重新登录或重启 `veil.exe`）。
  2. 每个档位打开 `docs/qa/syntax-matrix.md` 同一份语料，记录：首帧是否完整（无空白/半屏）、标题与正文基线是否清晰、表格网格线是否为 1 物理像素、窗口最大化/还原后版心是否重新居中。
  3. 在正文段落中点按、拖选、双击选词、三击选段各一次，确认光标落点与字形一致（误差 ≤1 个字符宽）。
  4. 打印预览/导出 PDF 各一次，确认页边距（毫米）在四个档位下一致（PDF 以 pt 输出，不应随屏幕 DPI 改变）。
  5. 每档截图（窗口整体 + 光标落点特写）存入 `docs/qa/evidence/dpi-<档位>-2026-11-27/`。
- 判定标准：四个档位首帧均完整、命中误差 ≤1 字符、版心与页边距一致；任一档位不满足即登记为缺陷，不得以「高分屏正常」代替。

### 1.2 实体物理打印机

- 状态：**NOT RUN**（打印只经 Microsoft Print to PDF 与原生 PDF 分页路径验证）
- 为什么不能自动化：需要真实打印机、纸张与驱动；应用内无独立打印预览，页数/断页只能由驱动回传或出纸核对。
- 可复现步骤：
  1. 打开含「短代码块 + 超过一页的长表格 + 图片」的文档（可用 `docs/qa/evidence/w10-2026-11-27/` 的样张源）。
  2. `Ctrl+Alt+P` → 选择实体打印机 → A4 → 打印。
  3. 核对：短代码块不跨页；长表格每页顶部有表头、断页落在行边界、无行被上下切开；页脚页码连续；总页数与 Microsoft Print to PDF 的页数一致。
  4. 拍照/扫描每页，存入 `docs/qa/evidence/physical-printer-2026-11-27/`。
- 判定标准：上述四项全部满足。驱动造成的字体度量差异（字宽/行高）按 `docs/review/evidence/layout-consistency-2026-11-26.md` 的「已接受的环境差异」处理，不作为缺陷。

### 1.3 真机中文 IME（微软拼音 / 微软五笔）

- 状态：**NOT RUN**（代码侧 IME 锚点与 preedit 绘制已有端口单测，真机六步走查未执行）
- 为什么不能自动化：候选窗由系统 IME 进程绘制，自动化无法稳定注入真实按键序列与选词。
- 可复现步骤（每个输入法各走一遍）：
  1. 段落中部输入 `nihao`，确认 preedit 下划线跟随光标、不越出版心。
  2. 按空格上屏「你好」，确认无重复字符、无光标跳动。
  3. 输入 `zhongguo` 后按数字键选第 2 候选，确认上屏文字正确。
  4. 在行首、行尾、表格单元格内各重复一次步骤 1–3。
  5. 输入中按 `Esc` 取消组合，确认文档字节不变。
  6. 输入中窗口失焦再回焦，确认候选窗位置与 preedit 状态一致。
- 判定标准：六步均无丢字/重字/错位；任一失败记录输入法版本、文档位置与截图。

### 1.4 Narrator / NVDA

- 状态：**不支持（已移除），不是 NOT RUN**
- 事实：AccessKit/UIA 层已于 `3a6d72d`（`refactor(ui)!: 永久移除无障碍（AccessKit）能力`）永久移除；`Cargo.lock` 无 `accesskit`，源码无可访问性树。中英 README 已同步更正。
- 结论：无障碍是明确非目标；不存在「待验证的语音流程」。历史范围文档 `docs/review/accessibility-scope-and-limits.md` 仅作存档，描述的能力已不存在。

### 1.5 其它沿用的人工项

以下项沿用 `README` 既有登记，本轮未重新执行，不改变其 NOT RUN 状态：

## 2. 延后项（本轮明确不做）

每条给出「为什么现在不做」与「何时重开」的判据；判据必须可观察，避免「以后再说」。

| 项 | 为什么现在不做 | 何时重开 |
|---|---|---|
| GPU / wgpu 渲染管线 | ADR-011 已裁决：击键 p95 的主项是索引重建与 CPU shaping/光栅，不是像素合成；引入 GPU 栈会挤压体积（≤15 MiB）与依赖（≤200）预算，增量未实测不得作为理由。 | ADR-011 四条触发条件任一成立：①4K/120Hz 大面积滚动实测掉帧且 profiler 显示 CPU 为主因；②内容区需要 Mica/亚克力；③需要文档级过渡动画且软件合成达不到目标帧率；④需要 GPU 侧公式/图片实时缩放。触发后先做独立 spike，再评审。 |
| Linux / macOS 桌面 | 产品定位 Windows-only：界面依赖 Win32/GDI 打印、DWM、UIA、系统字体与 IME；core 已跨平台并有 Linux CI，但 UI/产品层没有等价验证环境。 | 出现真实用户需求且愿意承担第二套平台集成与验证矩阵（打印、DPI、IME、无障碍四项都需重做）时。 |
| 移动端 / PWA | 交互模型（键盘优先、多级菜单、GDI 打印、本地文件）与触屏/沙箱浏览器不匹配；离线 Mermaid 与文件系统语义也不同。 | 明确以「只读预览 + 轻编辑」为独立产品时，而不是把桌面 exe 移植过去。 |
| 插件系统 | 会引入第三方代码执行、权限模型、版本兼容与体积/启动开销；当前能力边界（语法、导出、主题）尚未稳定到可冻结 API。 | 核心文档模型与渲染契约连续两个 minor 版本无破坏性变更，且出现至少三个无法用内置能力满足的真实扩展需求时。 |
| 协作 / 同步 | 需要账号、网络、冲突合并与服务端信任边界，与「无后台网络、无遥测」的现状直接冲突。 | 产品明确转向团队场景，并愿意单独立项做安全与隐私评审时。 |
| 表格合并/拆分单元格 | 需要单元格跨度模型、编辑操作、Markdown 序列化与六表面渲染的同步改造；当前表格已支持内容编辑、行列增删、对齐与列宽拖动。 | 出现必须以合并单元格表达的刚需文档，且确定 Markdown 扩展语法与导出兼容策略后。 |
| 独立富文本文档模型 | 正文真值必须是 Markdown 字节；引入第二套模型会破坏「源码/渲染同一份文本」的契约与测试矩阵。 | 不重开（产品反目标）；若未来支持其它格式，作为独立导入/导出层，不改正文真值。 |
| 图表渲染内置浏览器/WebView | 进程内 QuickJS + 完整 mermaid.js 已覆盖需求，且能保证离线、无 Chromium、无 `foreignObject`；WebView 会引入系统依赖与安全面。 | 出现 QuickJS 无法支持且无法离线降级的关键图型时，先评估独立渲染服务/预渲染方案。 |
| 宽表横向滚动的「表内独立滚动条」增强 | 本轮以「可读完」为最低目标实现横向平移与窄窗断言；独立滚动条属于交互增强，不影响正确性。 | 用户反馈需要同时并排查看多张宽表，或需要拖拽滚动条精确对位时。 |
