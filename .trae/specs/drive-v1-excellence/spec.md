# 驱动 v1 卓越质量（自动化走查 + 收尾 + 架构审查）Spec

> 状态：**提案，未执行**。本次仅落文档与 skill，未写产品代码；等待批准后进入 apply。
> 基线 commit：`c2673e2`（阶段 0 断行策略 + 探针）、`4fbb519`（veil-walkthrough-verify skill）。
> 基线指标：900 passed / 12 ignored、clippy 零警告、release 5,844,480 B、keystroke p95 1.07 ms。

## Why

v1 已接近发布，但质量验证仍依赖重复的人工走查：`3e-manual-walkthrough.md` 的 50 条用例中，8 条无自动化覆盖、7 条纯人工；C2/C5/D12-b/C7 与 E/F/G/H 未测区仍悬挂。人工走查的成本不在“点一次”，而在**每次改动后都要重复同一组窗口尺寸、滚动、截图、回填台账**，且结论难以复核。

同时，用户要求把应用推进到「完美的 Windows Markdown 应用」，并明确补充：**整体架构、每个 crate 的架构、每个 crate 内部的函数组织都必须先进、可靠、强大**。这两件事都必须先转化为可判定标准，否则「完美」没有终点，容易演变成无边界的重构或功能膨胀。

本 spec 的立场：**用分层自动化替代重复劳动；用可测口径替代「完美」；用审计驱动的小步修正替代架构重写。**

## What Changes

- **A. 走查自动化基建（分层，非像素级）**：新增 `tools/walkthrough.ps1`（启动/窗口尺寸/滚动/截图/探针收集/进程清理）+ 场景矩阵（把 50 条映射为 `auto / assisted / manual`）；证据落 `docs/review/evidence/` 或 `%TEMP%` 临时目录并回填台账。
- **B. v1.0 发布门禁**：把剩余 `needs-user` 项全部用脚本或人工证据回填；阻断项清零；红线复测；满足后 `git tag v1.0.0`。
- **C. v1.1 走查收尾**：表格单元格禁则（已确认根因 `Wrap::Glyph`）、C5 表格交互、D12-b 渲染/显隐归因、C7 图片覆盖、E/F/G/H 未测区；正文 C2 仅在用户提供原始复现场景后处理。
- **D. 排版细节对齐 Typora（可判定子集）**：不承诺像素一致，只承诺 C1/C2/C3/C5 单元格换行 + 行内对象/公式/图片/打印分页的行为一致。
- **E. 架构审计（六原则）**：按 `architecture-audit` 对 crate 边界与函数组织做审计；只修高严重度、有证据的问题，禁止为“统一风格”大改。
- **F. 文档真值与盲测**：README/台账数字与代码同步；执行 3–5 人盲测，3/5 无提示完成三项任务为通过线。
- **明确不做**：像素级 golden 截图断言、OCR 文本断言、把 GUI 脚本当 CI 硬门禁、架构重写、自研排版引擎、v2 功能（协作/CRDT/Mermaid/表格可视化编辑）。

## ADDED Requirements

### Requirement: 走查场景矩阵必须明确自动化等级

每条走查用例 SHALL 标注 `auto / assisted / manual` 三档之一，并写明证据形式（探针日志 / 截图 / 人工观察记录）。`auto` 必须能在无人值守下给出可复现的判定；`assisted` 由脚本执行动作、人工判定视觉结果；`manual` 仅限主观或破坏性场景（盲测、物理打印机等）。

#### Scenario: 断言等级

- **WHEN** 新增或修改一条走查用例
- **THEN** 场景矩阵同步更新等级与证据形式；没有等级的条目不得进入发布门禁统计

### Requirement: 任何「通过」都必须附证据

台账中的「通过」SHALL 关联至少一项证据：测试名、探针日志片段、截图文件、或人工记录（含日期/操作者/窗口宽度/文档）。未观察到真机结果前，状态只能保持「未解决」或「未测」。

#### Scenario: 回填

- **WHEN** 自动化脚本或人工执行完一条用例
- **THEN** 台账写入结果 + 证据路径 + 命令参数；缺证据的回填视为无效

### Requirement: GUI 自动化必须可清理、不抢焦点

脚本 SHALL 用进程 PID 定位窗口、结束进程、关闭临时文件；禁止依赖前台焦点发送按键，优先 `PostMessage`；执行前后不得改变用户其他窗口状态。脚本失败 MUST 在日志中区分「脚本失败」与「产品缺陷」。

#### Scenario: 中断恢复

- **WHEN** 脚本在滚动或截图阶段异常退出
- **THEN** 目标进程被终止、临时文件留在可定位目录、日志含失败步骤，不遗留孤儿窗口

### Requirement: v1.0 门禁定义

发布 v1.0.0 前 SHALL 同时满足：① 走查矩阵无 `needs-user` 悬挂；② P0/P1 阻断项为 0；③ 红线指标全部有当期实测；④ 字节往返一致率 100%；⑤ 崩溃/数据安全场景（G1–G9）全部有证据；⑥ 决策项（H2/U1/B7-3/I3）维持已收口。

#### Scenario: 不达标

- **WHEN** 任一条不满足
- **THEN** 不执行 `git tag v1.0.0`，台账写明阻塞项与所属计划档位

### Requirement: 排版对齐的定义必须是行为而非像素

「对齐 Typora」SHALL 表述为可观测行为：C1 中西文间距、C2 行首/行尾禁则、C3 满行悬挂、C5 单元格内换行与对齐、行内公式/图片垂直度量、打印分页一致性。禁止以像素级 golden 截图作为唯一验收。

#### Scenario: 表格单元格

- **WHEN** 窄列宽单元格内含中文标点
- **THEN** 自动换行后行首/行尾不出现禁则标点，且 Tab 跳格与点击定位不受影响

### Requirement: 架构审计必须有边界与退出条件

审计 SHALL 覆盖：workspace crate 边界、`veil-core` 零 GUI/零异步、`veil-ui` 三域分离与缓存失效入口、`chrome` 三责分离、函数职责与模块导出面。每项发现标注严重度与证据；高严重度必须修复或书面豁免（附理由与风险），禁止无证据的全量重构。

#### Scenario: 边界违规

- **WHEN** 审计发现某模块直接全量枚举块结构或缓存失效分散
- **THEN** 登记为高严重度，给出最小修正方案与回归测试；未修复前不得宣称架构达标

### Requirement: 盲测协议

盲测 SHALL 使用 3–5 名目标用户、同一组三项任务（改错别字并保存 / 新建写 200 字并插图 / 导出 HTML），记录完成时间、卡点与第一句理由；3/5 无提示完成且至少 2 人说出「快 / 不丢字 / 源码可信」之一为通过。

#### Scenario: 未达通过线

- **WHEN** 完成人数 <3 或无人给出三项理由之一
- **THEN** 结论记为「未通过」，进入体验改进任务，不得用自动化结果替代

## 阶段划分与影响/受益

### 阶段 A：自动化基建

**做什么**：场景矩阵、`tools/walkthrough.ps1`、截图与探针证据收集、台账回填模板。

**显著受益**：同一条用例可重复执行并留证；宽度扫描/深滚动这类高重复动作成本降到一次脚本；C2 类“单测过、真机不过”的差异第一次能被系统化捕获。

**负面/风险**：脚本本身需要维护；Win32 尺寸/DPI 差异会让截图不完全一致；`PostMessage` 在某些控件上可能不触发（需脚本层记录并降级为人工）；存在“脚本绿了但人看着不对”的假安全感。

**决策**：只做分层自动化，**不把脚本结果当发布门禁**；视觉判定仍由截图+人工终审。

### 阶段 B：v1.0 门禁

**做什么**：补齐 needs-user、清零阻断、复测红线、打 tag。

**显著受益**：发布有明确证据链；避免“凭感觉可发”。

**负面/风险**：破坏性用例（G 区）会改动真实文件，必须用临时目录/副本；`git tag` 后若发现缺陷需要 patch 版本，不能回退 tag。

**决策**：门禁项全部可测；主观项（盲测）单列，不混入阻断统计。

### 阶段 C：v1.1 收尾

**做什么**：C2 表格单元格、C5、D12-b、C7、E/F/G/H 未测区。

**显著受益**：把已知缺陷收敛到 0；表格与排版体验达到可对标桌面写作软件的水准。

**负面/风险**：C5 是复杂度集中区，修一处可能牵动命中/选区/滚动；D12-b 若归因到 reveal/缓存，改动会影响行高与光标缓存；C7 需要磁盘/剪贴板真实交互，测试环境依赖高。

**决策**：按「单元格断行 → 定位/Tab → 对齐 → 图片 → 打印/主题/数据安全」顺序，单点修复+回归，禁止一次性重构表格。

### 阶段 D：架构审计

**做什么**：按六原则审计 crate 与函数组织，修高严重度项。

**显著受益**：边界与职责可解释；减少缓存/几何真值分散导致的复发 bug；为 v2 留出扩展点。

**负面/风险**：审计容易变成“风格偏好”与大规模搬迁；任何跨 crate 改动都可能触及 900 条测试与性能红线；过度抽象会违背极简主义。

**决策**：审计先行、修复按证据；只允许“小步、可回滚、带回归”的改动；架构达标定义为“无高严重度 + 边界规则有测试/文档守卫”，不是“重写”。

### 阶段 E：发布与盲测

**做什么**：文档数字同步、Release Notes、3/5 盲测、tag。

**显著受益**：对外承诺与实测一致；用户体验有真实证据。

**负面/风险**：盲测需要真实用户时间，不能自动化；样本小，结论只能作为方向性证据。

**决策**：盲测是发布门禁的一部分，但不替代自动化；未达线则记录并进入改进，不伪造通过。

## 质疑与反证（为什么不是别的方案）

1. **为什么不做像素级 golden 截图？** DPI、字体 fallback、抗锯齿、窗口边框都会导致像素漂移；维护基线图的成本高于收益。截图只作证据与人工复核，不作自动化断言。
2. **为什么不用 OCR 判定文字？** 中文 OCR 对细小字号/抗锯齿误差敏感，误报会污染台账；排版问题应通过 `VEIL_BREAK_PROBE` 等确定性探针判定。
3. **为什么不做完整 GUI E2E 作为 CI 门禁？** 原生窗口自动化易受焦点/桌面会话影响，CI 上不稳定；保留脚本作为本地证据工具。
4. **为什么不现在重写架构？** 当前 900 测试全绿、红线有余量，重写收益无法量化且风险高；用审计找高严重度问题，小步修。
5. **为什么不自研排版引擎？** 阶段 0 已证明正文路径干净、表格路径是 `Wrap::Glyph` 的选择问题；引擎级重写不解决局部缺陷。
6. **为什么正文 C2 不直接改？** 真机与 headless 均未复现，先要求用户提供原始场景；否则会为不存在的路径写补丁。
7. **「完美」为什么不定义为“零缺陷”？** 零缺陷不可证；用 50 条矩阵 + 红线 + 架构审计 + 盲测四条可测口径定义“卓越”，避免无边界扩张。

## 可判定完成标准（Excellence Scorecard）

- 走查矩阵：50/50 条目有等级与证据；无 `needs-user`、无未测。
- 阻断：P0/P1 = 0；已知缺陷表仅剩已决策降级项（H2/U1/B7-3/I3 口径不变）。
- 红线：冷启动 ≤300ms（应用内口径）、keystroke p95 <16ms、内存 ≤150MB、exe ≤15MiB、往返 100%、`veil-core` GUI 依赖 0。
- 排版：C1/C2/C3 通过；C5 单元格换行禁则 + Tab/点击；公式/图片/打印分页无截断错位。
- 数据安全：G1–G9 全有证据；崩溃恢复、外部修改备份、文件缺失重建均通过。
- 架构：六原则审计无高严重度；`veil-core` 零 GUI、`veil-ui` 三域边界有测试或文档守卫。
- 盲测：3/5 无提示完成三项任务，≥2 人给出「快/不丢字/源码可信」之一。
