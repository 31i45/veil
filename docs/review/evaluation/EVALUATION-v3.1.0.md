# Veil v3.1.0 评价报告

> 日期：2026-11-28｜基线：`main`（v3.0.2 之后 143 个提交）｜版本：3.1.0
> 方法：只读代码与文档审计 + 本机真实命令输出；人工未执行项一律写 NOT RUN，不折算成 PASS。
> 本报告回答一个问题：Veil 现在是否「完美」？答案是否定的；以下是它达到了什么、没达到什么、以及为什么。

## 0. 结论（三句话）

1. **工程化程度高，但不是完美产品**：全量测试、clippy、格式、语法矩阵、发布门禁都有真实输出；仍存在巨型模块、stringly 错误、双解析器、兼容性证据缺口与签名信任缺口。
2. **Markdown 主路径接近一流，但没有 100% 跨面一致**：CommonMark 652 例结构 A/C/D 全过，但精确 HTML 为 629/652；GFM 23 例结构全过，规范化 HTML 仅 12/23；PDF/打印对远程图片降级、断行与屏幕存在已归因差异。
3. **可以发布 v3.1.0，但只能按「本地单机、未获生产信任背书」的口径发布**：生产签名、真实 SmartScreen、跨机信任、外部安全审计、真实断网抓包均未完成。

## 3. 十几个子系统的真实状态

Veil 不是一个「大文件应用」，而是四个 crate 的明确分工：

- `veil-core`：rope 存储、增量块解析、行内解析、注解、公式/高亮、序列化与往返一致。
- `veil-ui`：`view`（派生状态与缓存）、`chrome`（菜单/浮层几何与绘制）、`interaction`、`paint`、`print`、`theme`、`i18n`、`tokens`。
- `veil-mermaid-offline`：QuickJS + linkedom + 完整 mermaid.js 的进程内渲染，惰性初始化。
- `veil`：平台接缝（Win32 窗口、文件监听、原子 IO、WinHTTP、打印、PDF、导出、对话框、单实例）与产品装配。

接缝的强项是「机制与策略分离」：内核只提供原语，交互策略在视图层；平台能力以 trait 注入，`veil-ui` 保持 headless 可测。弱项同样明确：`pdf_layout.rs`、`block.rs`、`export.rs`、`interaction.rs` 都是数千行的巨型模块，评审成本高；错误类型在端口层退化为字符串。

## 4. 与顶级产品原则的对照

| 原则 | 达成 | 未达成 |
|---|---|---|
| 第一性原理 | 离线契约、字节可逆、「字不会丢」先于功能；ADR-011 用 shaping 成本否决 GPU | 文档与实现之间缺少自动校验回路（本轮靠人工审计发现漂移） |
| 二八定律 | 主路径：打开、写、保存、查找、导出、打印；低收益项明确不做 | 仍保留了 Mermaid 全图型离线引擎这类高成本能力，体积换能力 |
| 软件设计的哲学 | 信息隐藏、单一门面、无环依赖 | 双解析器、巨型模块、`App` 字段超目标 |
| UNIX 哲学 | 纯函数化断行、`veil-core` 零平台依赖、工具脚本可组合 | 产品是单进程 GUI，无法以文本流组合；这是定位而非缺陷 |
| 少即是多 / 极简 | 界面三档字号、4 的倍数间距、单 accent、≤160 ms 动效 | 设置项 17 个键（13 可编辑）已接近「需要搜索」的复杂度 |
| 极致美学 | 对比度可断言、令牌单源、浮层单线 | 极端主题与高 DPI 的观感仍需人眼终验 |
| 极致 UX | 焦点闭环、错误不静默、失败文案给下一步 | DPI 逐档命中与五笔输入法仍是证据缺口 |

## 6. 放行判断

v3.1.0 可以作为「本地优先、离线、单机」的 Windows Markdown 写作工具发布，发布口径必须包含：**未获得生产签名信任、真实 SmartScreen 与跨机验证未执行、部分人工证据 NOT RUN**。

不得声称：完美、100% Markdown 兼容、全平台可用、零出站已验证、生产可信签名。
