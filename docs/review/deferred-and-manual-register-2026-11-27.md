# 延后项与人工验证登记（2026-11-27）

> 依据：`docs/qa/perfect-surface-audit-2026-11-27.md`（F 台账）与 `.trae/specs/converge-perfect-writing-surface/spec.md` 的「证据闭合与延后登记」需求。
> 本文只做两件事：把**确实需要人在场或硬件**的验证项写成可复现步骤与判定标准；把**本轮明确不做**的能力写成「为什么现在不做 + 何时重开」。
> 约定：未执行的项一律写 **NOT RUN**，不写成「预期通过」。

## 1. 人工验证项（需人在场 / 需硬件）

自动化能覆盖的部分已由测试固定；以下项因涉及系统设置、物理设备或真人输入法交互，本轮不伪造结果。

### 1.1 系统 DPI 100% / 125% / 150% / 200%

- 状态：**100% / 125% / 150% / 200% 四档首帧全部 PASS（2026-11-28，真实切换系统缩放）**；**逐档点按/拖选命中 NOT RUN**（未逐档做人工命中核对，不把「首帧完整」冒充「全部判定项通过」）。
  四档窗口物理尺寸 916×739 / 1143×922 / 1372×1106 / 1826×1335，随缩放线性变化；首帧文字清晰、无空白/半屏/裁切。打印/导出页边距为毫米制、不随屏幕 DPI 变，已有 PDF 断言。
- 证据：`docs/qa/evidence/assisted-2026-11-27/dpi-100.png`、`dpi-125.png`、`dpi-150.png`、`dpi-200.png` 与
  `docs/qa/evidence/assisted-2026-11-27/dpi.jsonl`（四档均 `status=PASS`）
- 为什么不能自动化：DPI 是 Windows 显示设置的系统级状态，切换会改变所有进程的物理像素映射，通常需要注销/重启，且会干扰同一台机器上的其它工作；headless 测试只能改逻辑缩放因子，不能证明系统 DPI 切换后的真实首帧、命中与版心。
- 协同方式（步骤已改为 assisted 脚本驱动，用户只做物理切换）：
  1. `pwsh -NoProfile -File tools/verify/assisted/dpi.ps1` 查看当前档位；
  2. 按提示手动切换 Windows 缩放并重新登录（或完全重启 `veil.exe`）——这是唯一需要用户做的物理动作；
  3. 对目标档位执行 `pwsh -NoProfile -File tools/verify/assisted/dpi.ps1 -Dpi <100|125|150|200> -Capture`：
     脚本读取系统/窗口 DPI、启动 release `veil.exe` 打开 `docs/qa/syntax-matrix.md`、等首帧稳定、抓整窗图、
     追加一行 JSON 到 `dpi.jsonl`；请求档位与实测不一致时写 `NOT_RUN` 且**不产生 png**。
- 用户下一步只需：切换缩放 → 重新登录 → 执行第 3 条命令（换一个档位重复）。
- 判定标准（不变）：四个档位首帧均完整（无空白/半屏）、标题与正文基线清晰、表格网格线为 1 物理像素、窗口最大化/还原后版心重新居中；在正文段落中点按、拖选、双击选词、三击选段各一次，光标落点与字形误差 ≤1 字符宽；打印预览/导出 PDF 的页边距（毫米）四档一致。任一档位不满足即登记为缺陷，不得以「高分屏正常」代替。

### 1.2 实体物理打印机（可选冒烟，不是发布门禁）

- 状态：**NOT RUN（可选）**，不阻塞收口。`Microsoft Print to PDF` 是真实打印驱动，已覆盖应用侧分页正确性（页数、每页表头、行边界、页码）；实体出纸只额外验证驱动缩放/边距与介质差异，换一台打印机结论就可能不同，不是软件正确性。自动部分已完成：样张、`Get-Printer` 枚举与核对清单已生成
- 证据：`docs/qa/evidence/assisted-2026-11-27/print-sample.md`（短代码块 + 80 行跨页长表 + 图片）、
  `print-checklist.md`（识别到实体打印机 `Pantum CM230DN Series 0001`；六项出纸核对均为 `PENDING`）
- 为什么不做门禁：实体出纸依赖具体驱动与纸张，结果不可跨设备复现；把它当发布门禁既不能证明代码更正确，也无法覆盖其他型号。应用必须在「PDF / Print-to-PDF」这一层正确，这是可复现的。
- 何时重开：只有当用户实际从 Veil 直接打印到某台实体机并遇到出纸问题，或明确要求出纸核对时，才对那个型号做一次冒烟；结果记为该型号的一次性核对，不进入每轮门禁。
- 协同方式（步骤已改为 assisted 脚本驱动，可选执行）：
  1. `pwsh -NoProfile -File tools/verify/assisted/print.ps1`：生成样张/清单并打开应用（无人值守加 `-NoLaunch`）；
  2. 用户装 A4 纸 → `Ctrl+Alt+P` → 选择清单中的实体打印机 → A4 → 打印；
  3. 在 `print-checklist.md` 中逐项核对并把 `PENDING` 改为 `PASS`/`FAIL`，附照片路径；无实体打印机时整节记 `SKIP`。
- 若决定做这次可选冒烟：装纸后执行 `pwsh -NoProfile -File tools/verify/assisted/print.ps1`，再按 `Ctrl+Alt+P` 打印并核对出纸；不做也不阻塞收口。
- 判定标准（不变）：短代码块不跨页；长表格每页顶部有表头、断页落在行边界、无行被上下切开；页脚页码连续；总页数与 Microsoft Print to PDF 的页数一致。驱动造成的字体度量差异（字宽/行高）按 `docs/review/evidence/layout-consistency-2026-11-26.md` 的「已接受的环境差异」处理，不作为缺陷。

### 1.3 真机中文 IME（微软拼音 / 微软五笔）

- 状态：**微软拼音六步 PASS（2026-11-28，真实按键驱动）**；**微软五笔 NOT RUN（系统未安装）**。
  已证实：预编辑下划线跟随光标且候选窗不越出版心；空格上屏「你好」无重复；`zhongguo` 选第 2 候选得「中过」；
  行首/行尾与表格单元格内输入均正确落位；`Esc` 取消后文件哈希与基线完全一致。
  行为记录（P2 观察，未当缺陷关闭）：组合未上屏时失焦，IME 把原始串 `nihao` 提交进文档（系统语义，不丢字、不重复）。
- 证据：`docs/qa/evidence/assisted-2026-11-27/ime-result.md` 与 `ime-step1-preedit.png`、`ime-step2-commit.png`、`ime-step3-candidates.png`、`ime3-table-commit.png`、`ime2-esc-after.png`、`ime2-focus-*.png`
- 为什么不能自动化：候选窗由系统 IME 进程绘制，自动化无法稳定注入真实按键序列与选词。
- 协同方式（步骤已改为 assisted 脚本驱动，用户只输入/切输入法）：
  1. `pwsh -NoProfile -File tools/verify/assisted/ime.ps1`：启动 release `veil.exe` 并逐步提示；
  2. 用户把输入法切到「微软拼音」，按六步操作：①段落中部输入 `nihao`，确认 preedit 下划线跟随光标、不越出版心；
     ②空格上屏「你好」，确认无重复字符、无光标跳动；③输入 `zhongguo` 后按数字键选第 2 候选；
     ④在行首、行尾、表格单元格内各重复一次①–③；⑤输入中按 `Esc` 取消组合，确认文档字节不变；
     ⑥输入中窗口失焦再回焦，确认候选窗位置与 preedit 状态一致。每一步完成回车；
  3. 脚本每步自动截图 `ime-step-<n>.png`，最后询问六步结论并生成 `ime-result.md`（六步/用户观察/截图路径）。
     `-Preflight` 只登记 `NOT RUN`，不启动应用。
- 用户下一步只需：执行 `pwsh -NoProfile -File tools/verify/assisted/ime.ps1`，按提示打字/切输入法（微软五笔再跑一遍）。
- 判定标准（不变）：六步均无丢字/重字/错位；任一失败记录输入法版本、文档位置与截图。

### 1.4 Narrator / NVDA

- 状态：**不支持（已移除），不是 NOT RUN**
- 事实：AccessKit/UIA 层已于 `3a6d72d`（`refactor(ui)!: 永久移除无障碍（AccessKit）能力`）永久移除；`Cargo.lock` 无 `accesskit`，源码无可访问性树。中英 README 已同步更正。
- 结论：无障碍是明确非目标；不存在「待验证的语音流程」。历史范围文档 `docs/review/accessibility-scope-and-limits.md` 仅作存档，描述的能力已不存在。

## 2. 延后项（本轮明确不做）

每条给出「为什么现在不做」与「何时重开」的判据；判据必须可观察，避免「以后再说」。

| 项 | 为什么现在不做 | 何时重开 |
|---|---|---|
| GPU / wgpu 渲染管线 | ADR-011 已裁决：击键 p95 的主项是索引重建与 CPU shaping/光栅，不是像素合成；引入 GPU 栈会挤压体积（≤15 MiB）与依赖（≤200）预算，增量未实测不得作为理由。 | ADR-011 四条触发条件任一成立：①4K/120Hz 大面积滚动实测掉帧且 profiler 显示 CPU 为主因；②内容区需要 Mica/亚克力；③需要文档级过渡动画且软件合成达不到目标帧率；④需要 GPU 侧公式/图片实时缩放。触发后先做独立 spike，再评审。 |
| Linux / macOS 桌面 | 产品定位 Windows-only：界面依赖 Win32/GDI 打印、DWM、UIA、系统字体与 IME；core 已跨平台并有 Linux CI，但 UI/产品层没有等价验证环境。 | 出现真实用户需求且愿意承担第二套平台集成与验证矩阵（打印、DPI、IME、无障碍四项都需重做）时。 |
| 移动端 / PWA | 交互模型（键盘优先、多级菜单、GDI 打印、本地文件）与触屏/沙箱浏览器不匹配；离线 Mermaid 与文件系统语义也不同。 | 明确以「只读预览 + 轻编辑」为独立产品时，而不是把桌面 exe 移植过去。 |
| 插件系统 | 会引入第三方代码执行、权限模型、版本兼容与体积/启动开销；当前能力边界（语法、导出、主题）尚未稳定到可冻结 API。 | 核心文档模型与渲染契约连续两个 minor 版本无破坏性变更，且出现至少三个无法用内置能力满足的真实扩展需求时。 |
| 协作 / 同步 | 需要账号、网络、冲突合并与服务端信任边界，与「无后台网络、无遥测」的现状直接冲突。 | 产品明确转向团队场景，并愿意单独立项做安全与隐私评审时。 |
| 表格合并/拆分单元格 | 需要单元格跨度模型、编辑操作、Markdown 序列化与六表面渲染的同步改造；当前表格已支持内容编辑、行列增删、对齐与列宽拖动。 | 出现必须以合并单元格表达的刚需文档，且确定 Markdown 扩展语法与导出兼容策略后。 |
| 独立富文本文档模型 | 正文真值必须是 Markdown 字节；引入第二套模型会破坏「源码/渲染同一份文本」的契约与测试矩阵。 | 不重开（产品反目标）；若未来支持其它格式，作为独立导入/导出层，不改正文真值。 |
| 图表渲染内置浏览器/WebView | 进程内 QuickJS + 完整 mermaid.js 已覆盖需求，且能保证离线、无 Chromium、无 `foreignObject`；WebView 会引入系统依赖与安全面。 | 出现 QuickJS 无法支持且无法离线降级的关键图型时，先评估独立渲染服务/预渲染方案。 |
| 宽表横向滚动的「表内独立滚动条」增强 | 本轮以「可读完」为最低目标实现横向平移与窄窗断言；独立滚动条属于交互增强，不影响正确性。 | 用户反馈需要同时并排查看多张宽表，或需要拖拽滚动条精确对位时。 |
| 打印路径「高于一页的显示公式」逐块缩放 | **已修复（2026-11-27，Task 3）**：打印路径改为与 PDF 同规则——单条显示公式高于一页时等比缩放到一页可用高内（打印取页帧高 × 80%，PDF 取 `content_h - 12pt`），块高度/绘制/命中同口径，不再按页底硬切。历史：此前打印块高取已渲染位图像素、无打印专用缩放，超高公式按页底硬切并在续页继续（两路径都不丢内容）。 | 已闭合；若再次复现「打印/PDF 公式跨页或公式块命中错位」，按回归失败重开：`print_scales_tall_display_math_to_one_page`、`tall_display_math_scales_to_single_page_content_height`。 |

## 4. 重开流程

任一延后项触发重开时：先在本文件追加「触发证据」（实测数据或用户需求记录），再在 `docs/adr/` 立项，按 ADR-008 的单 commit、可回滚纪律实施；不得以「顺手做了」的方式混入无关提交。
