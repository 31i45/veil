# ADR-008: 依赖升级策略

## 状态：已采纳（2026-10-25）

## 背景

2026-10-25 代码审计发现两类依赖漂移：① 版本滞后——`cosmic-text` 钉在 0.12，上游已到 0.19；② 同 crate 多版本并存——`ttf-parser` 出现 3 个版本、`png` 出现 2 个版本等，传递依赖树在去重口径下被放大。根因是此前没有升级纪律：既没有定期升级的触发点，也没有升级后同步回写数字红线的要求。

## 决策

1. **每切片完成后允许 `cargo update`（minor/patch）**：作为切片收尾的常规动作，随切片 commit 一起进入版本库。
2. **major 升级单独立项**：独立 commit、不与功能改动混合，必须可 `git revert` 干净回滚；升级前先出迁移清单（API 变更点、受影响模块、测试预案），评审通过后执行。
3. **数字同 commit 回写**：升级引起的一切数字变化（测试数、依赖数、产物体积等）必须与 `.skills/INSTANCE.md` 的更新同 commit 提交，禁止数字与代码分离漂移。
4. **既有约束不变**：依赖黑名单（`tokio`、`wasmtime`、`webview2-com`/`wry` 等一切 webview）与 `veil-ui`+`veil` 直接依赖预算 8/8 不因升级而放宽。

## 后果

- 好：升级纪律化，安全修复与上游改进可持续进入；数字红线与依赖树始终同步，不再漂移；多版本并存问题在每次切片收尾时有机会收敛。
- 坏：major 升级流程成本增加（立项、迁移清单、评审），短期放慢大版本跟进速度；v1 阶段可接受。

## 替代方案

- **永不升级**：拿不到安全修复与上游缺陷修复，`cosmic-text` 类滞后会持续累积，否决。
- **无门禁随意升**：本项目已实证会漂移（版本滞后与多版本并存即其产物），且数字红线失去约束力，否决。
