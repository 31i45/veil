# ADR-011: GPU 渲染管线（wgpu）—— v1 不引入，改为触发式立项

## 状态：已采纳（2026-11-03）：v1 不做；触发条件满足时按本 ADR 重新立项

## 背景

v1 的呈现管线是 winit + softbuffer 软件呈现 + cosmic-text 排版 + 自绘 chrome（ADR-005），README 将「wgpu/GPU 渲染视图」列为 v1 非目标。2026-11-03 复核「是否应改用 GPU 管线」时，需要把这个裁决从口头约定固化为可检验的文档：既写清不做的理由，也写清什么情况下必须重开。

本次复核使用的实测数据（2026-11-03，`--release`，每档 300 次单字符插入，见 `docs/review/keystroke-attribution.md`）：

| 事实 | 数值 | 证据 |
|---|---|---|
| 击键 p95 中索引层占比 | 优化前 65.5% / 72.9% / 77.0%；优化后 28.2% / 34.0% / 35.8%（5,005 / 10,500 / 19,999 块） | keystroke-attribution 表 2 / 最终复测表 |
| 击键 p95 中 core 重解析 + 脏块排版 + 光栅合计 | 约 22%~32%（五段合计 p95 口径） | 同上 |
| 产物体积红线 / 当前 | ≤ 15 MiB / 5.56 MiB | INSTANCE §2 |
| 传递依赖红线 / 当前 | ≤ 200 / 141 | INSTANCE §2 |

## 决策

1. **v1 不引入 wgpu**：不新增 GPU 依赖，不替换 softbuffer 呈现层，不纳入默认路线图。
2. **仅在触发条件满足时按本 ADR 立项**；任一条触发后，先做 spike，再评审，再实施。
3. **前置顺序不可颠倒**：`spikes/` 独立 spike（体积、依赖、冷启动、p95 四项实测）→ ADR 立项（把实测增量填回本 ADR）→ 单 commit 实施且可回滚（对齐 ADR-008 的 major 升级纪律）。
4. **本 ADR 不写任何 wgpu 的体积/依赖增量估计**；所有增量必须由 `spikes/` 的独立 spike 实测后填入，未实测数字不得进入决策依据。

## 理由

（只列事实）

1. **两条硬约束会被挤压**：产物体积 ≤15 MiB（当前 5.56 MiB）、传递依赖 ≤200（当前 141）。GPU 后端栈会同时增加链接期体积与依赖树；具体增量未实测，须由 spike 填入。
2. **wgpu 不解决真正瓶颈**：Markdown 编辑器的耗时在脏块 shaping 与增量解析，两者都是 CPU 工作。本次实测击键 p95 中 core 重解析 + 脏块排版 + 光栅合计约 22%~32%，而索引层优化前曾占 65%~77%（本文写作时已通过 Block 字节区间 + 几何复用降至 28%~36%）；无论优化前后，慢的都在索引重建与解析结构，不在像素合成。换 GPU 管线不会缩短这两段。
3. **极简栈已是既定决策**：ADR-005 已确立自绘 chrome + 软件呈现 + cosmic-text 的极简栈（零 GL 上下文、零事件双轨）。引入 wgpu 会推翻该 ADR 的前提，需重新论证 chrome、光栅缓存、图片/公式管线与打印路径（打印走 GDI 干净帧，与 GPU 无关）。
4. **当前需求侧没有缺口**：Mica 由 DWM 标题栏提供（内容区纯色兜底，ADR-007）；无文档级过渡动画需求；公式/图片缩放是 CPU 光栅缓存命中问题，实测脏块排版与光栅合计在 0.4 ms 量级。

## 触发条件

以下四条任一成立，才允许按本 ADR 立项；每条都必须有 spike 数据，不能凭体感：

1. 4K/120Hz 大面积滚动实测掉帧，且 profiler 显示 CPU（shaping/光栅/合成）为主因。
2. 内容区需要 Mica/亚克力（不只是标题栏区域）。
3. 需要文档级过渡动画（页面切换、块级动画），且软件合成无法达到目标帧率。
4. 需要 GPU 侧公式/图片实时缩放（连续缩放/旋转使 CPU 光栅缓存持续失效）。

## 否决的替代方案

| 方案 | 结论 | 理由 |
|---|---|---|
| 现在就引入 wgpu | 否决 | 见理由 1–3；无当前收益，对体积/依赖预算的冲击未量化——须先 spike |
| vello | 否决（暂不） | 向量渲染库本身通常经 wgpu 落地，等于同时引入 wgpu 与一套新 2D 管线；体积/依赖增量未实测；当前文本瓶颈在 CPU shaping，vello 不消除 |
| skia（skia-safe / 预编译二进制） | 否决（暂不） | C++ 构建与二进制体量、绑定依赖、跨平台维护面都与「单文件 ≤15 MiB、无外部运行时」冲突；无当前收益，增量须 spike 实测后才有讨论价值 |
| 自研 GPU 后端（DX12/Vulkan + 自绘字形图集） | 否决（暂不） | 维护面最大（设备/交换链/字形图集/裁剪/DPI/驱动差异/回退路径），且不解决本次实测的 CPU 主项；属 v2 之后的独立子系统 |
| 保持软件管线 + 优先改造索引 | 采纳（本次，已落地） | 索引层优化前占击键 p95 65%~77%，是唯一有实测依据的收益点；已通过 Block 字节区间 + 几何复用降至 28%~36%，击键合计 p95 由 13.8 ms 降至 5.2 ms（10.5k 块） |

## 后果

- 好：v1 不付 GPU 依赖与产物体积预算；不引入第二个渲染后端，测试矩阵与打印路径保持单一；把「为什么不做」和「何时重开」写成可验证条件，避免以后凭体感反复争论。
- 坏：4K/120Hz 大面积滚动、内容区材质、文档级动画、GPU 侧实时缩放四类体验延后；若未来触发，GPU 后端是全新子系统，工作量与验证成本独立于 v1。
- 风险/约束：四条触发条件都必须先有 spike 数据；未实测的 wgpu 体积/依赖增量不得作为理由或结论写入任何文档（本 ADR 已按此执行）。立项后按 ADR-008 走单 commit、可 revert 的流程。
