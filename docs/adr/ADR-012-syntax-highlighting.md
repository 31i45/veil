# ADR-012: 代码块高亮迁移到 syntect（fancy-regex）—— 条件 Go

## 状态

已采纳（2026-11-16）。依据：`docs/review/component-replacement-spike.md` S1、S1-b。

## 背景

代码块高亮原为自研逐行状态机，覆盖 17 套语言文法（别名归一后 19 个规范名），无主题生态。按「能纯集成覆盖的模块优先用成熟组件」的目标，对 `syntect` 5.3.0 做了 spike。

S1 初测按「每次布局都重算整块」估算，得到 42–152 ms / 1000 行的数据并给出 No-Go。复核发现该模型与实现不符：布局层已有因果键缓存，只有被编辑块或光标进出块时才重排；syntect 官方也支持缓存 `ParseState` 并从改动行重启。据此补做 S1-b：fancy 后端 + 逐行 `ParseState` 缓存。

## 实测

同一 10 语言 × 1000 行固定语料、同一 release 配置（`lto=true` / `codegen-units=1` / `panic=abort`），Windows 11 x64。

### 体积与依赖

| 指标 | 结果 |
|---|---|
| exe 增量 | +2,023,424 B（集成后实测 9,784,832 B） |
| 叠加 `toml_edit` 后 exe | 9,784,832 B（10 MiB 红线内，余量 700,928 B） |
| syntect 依赖子树（去重） | 48（spike 独立工程口径；workspace 门禁 200，基线 101） |
| `SyntaxSet` 冷加载 | 0.9 ms（惰性：首次遇到代码块才加载） |
| 常驻内存（加载后 / 1000 行 Rust 后） | 7.1 MB / 22.2 MB 增量 |

### 增量复核（S1-b，`spikes/syntect-size/src/bin/incr_bench.rs`）

| 场景 | p50 | p95 | 重解析行数 |
|---|---|---|---|
| 100 行块，行首/中间/行尾单字符编辑 | — | 0.168 / 0.232 / 0.185 ms | 中位数 1，最大 2–4 |
| 1000 行块，行首/中间/行尾单字符编辑 | — | 0.478 / 0.449 / 0.393 ms | 中位数 1，最大 2–4 |

首次完整高亮（无缓存）：20 行 49.9 ms（含语法集预热离群值）、50 行 5.3 ms、100 行 10.2 ms、200 行 19.4 ms、500 行 52.7 ms、1000 行 101.4 ms。

## 决策

集成 `syntect`（`default-features = false` + `default-syntaxes` + `regex-fancy`），替换自研状态机，单一实现，不开运行时开关。

实现约束：

1. `SyntaxSet` 用 `OnceLock` 惰性加载，启动时零成本；只在首次排版代码块时加载。
2. 逐行缓存 `ParseState`：行文本与行首状态都未变即复用该行 token，单字符编辑只重解析受影响行。
3. 缓存按块起始偏移寻址并设 LRU 上限（64 块 / 2048 行），块 id 每次重解析都会变化，不能作为缓存键。
4. 输出契约不变：仍为 `(start, end, TokenKind)` 致密段，`layout`/`paint`/复制/打印/导出全部不改。
5. scope → `TokenKind` 由固定前缀表映射；`storage.type` 统一视为关键字（默认语法集把 Rust 的 `let`/`fn` 与 `u32` 放在同一 scope，无法在不重引入词表的前提下细分）。

## 理由

1. **同步排版延迟不是阻塞项**：编辑时只重解析改动行，1000 行块 p95 < 0.5 ms；整块首次高亮只在首次显示时发生一次。
2. **体积在红线内**：fancy 增量约 1.9 MiB，叠加配置组件后仍低于 10 MiB 目标；不引入 Oniguruma 静态库。
3. **纯 Rust**：fancy-regex 无 C 依赖，交叉编译与安全审计成本低于 onig。
4. **单一实现**：删除 1000+ 行自研状态机与 19 套词表，语言覆盖从 19 个规范名提升到默认语法集 75 套。

## 后果

- 语言覆盖：17 个既有规范名由 syntect 默认语法集覆盖；`toml` 与 `dockerfile` 不在默认集中，回退纯文本（不着色）。补齐需要引入额外语法集（第三方 dump 体积或自写文法维护成本），单独立项。TypeScript 继续复用 JavaScript 语法。
- 大块首次显示有一次性卡顿：>200 行代码块首次布局约 20–101 ms。块布局本身已有 64 KiB / 512 行上限，最坏约 53 ms；后续编辑走增量路径。若实测影响明显，再评估「首帧只高亮可见行」的异步方案。
- 未知语言与未覆盖语言统一降级为纯文本，不显示错误。
- 颜色语义接近但不逐一等值：例如 C 的 `int`、Rust 的 `u32` 归入关键字色，C++ 模板参数、YAML 键的着色与旧实现不同。

## 否决的替代方案

| 方案 | 结论 | 理由 |
|---|---|---|
| 保留自研 17 语言状态机 | 否决 | 语言覆盖与主题生态不足，维护成本高于组件替换 |
| syntect + onig | 否决 | 需要 C 静态库与构建工具链，体积优势不足以抵消可移植性成本 |
| syntect + 主题包（default-themes / two-face） | 否决 | 本项目用固定 7 色语义色板，不需要主题生态；额外语法集体积超红线 |
| 只对未覆盖语言用自研状态机 | 否决 | 双实现、两套状态与测试面，违反单一实现约束 |
| 把高亮移出动同步排版路径（异步） | 暂缓 | 当前增量数据已满足击键门禁；若大块首帧成为实际痛点再立项 |
