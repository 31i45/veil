# Architecture Audit

对 Veil 的整体架构和内部实现进行系统性审计。输出是一份基于证据的分析报告，不修改任何代码。

## 前置动作

开始审计前，按以下顺序获取上下文：

1. 读顶层 `Cargo.toml` — 确认 workspace 结构、依赖红线
2. 读 `README.md` — 确认项目定位、非目标、数字红线、ADR 导航
3. 读每个 crate 的 `Cargo.toml` — 确认依赖边界
4. 读每个 crate 的 `src/lib.rs` — 确认公开 API 面、模块划分、注释中的设计意图
5. 读核心模块的公开文件 — `session.rs` / `buffer.rs` / `history.rs` / `syntax/mod.rs` / 视图层入口

只在需要时深入子模块。不要一开始就全量扫描。

## 审计框架

按以下六个原则逐层展开。每个原则都要同时给出"做得好的地方"和"可以改进的地方"，只在有证据时才发言。

### 1. 第一性原理（First Principles）

追问每个设计的本质问题：
- 为什么必须这样设计？如果去掉这个设计，什么会坏掉？
- 是否存在隐含的第二真值？（如 AST 和源码同时维护）
- 抽象边界是否准确？（内核 vs 视图 vs 平台的分界）
- 性能假设是否被数据支撑？（如 mark 用 Vec 存是因为 mark 少，红线实测验证了这一点）

### 2. UNIX 哲学（Modularity）

每个模块做一件事，做对：
- 模块职责是否单一？是否有模块同时做两件不相干的事？
- 模块间接口是否窄？是否有内部类型向外泄漏？
- 模块拆分是否过碎（参数传递爆炸）？还是过粗（职责混杂）？
- 组合性如何？能否单独 headless 测试？

### 3. 二八定律（Pareto Principle）

识别关键 20% 的设计决策：
- 哪 5-8 个决定定义了产品 80% 的质量？
- 每个关键决定是否有 ADR 或等价文档钉死？
- 是否存在过度工程（为 0.1% 场景付出 20% 复杂度）？

### 4. 极简主义（Minimalism）

尽可能少：
- 直接依赖数、传递依赖数、产物体积、常驻内存，与同类产品对比
- 公开 API 的方法/类型数量，是否有 getter 泛滥或 Option hell
- 明确列出的"非目标"是否清晰？是否在主动拒绝功能
- 命名是否与事实一致？（如 crate 名不该叫 egui 却实际无 egui 依赖）

### 5. 代码整洁之道（Clean Code）

- 命名是否自解释？是否有歧义或过泛？
- 注释解释的是"为什么"还是"做什么"？关键算法是否有逐行注释？
- 测试覆盖：单元测试数、属性测试、集成测试、e2e
- Clippy 告警、fmt 一致性、unsafe 使用

### 6. 软件设计哲学（Software Design）

- 机制与策略是否分离？
- 依赖是否倒置？（上层定义 trait，下层实现）
- 错误处理是否分层？（内核严格 / 视图容错）
- 派生数据是否与真值数据分离？

## 证据纪律

- 每个判断必须能定位到具体文件/行号/ADR 编号
- 性能相关判断必须引用红线实测数据
- 命名建议必须列出所有受影响位置的清单
- 如果后续发现之前的判断有误，必须显式纠正并说明原因
- 诚实 vs 讨好：如果项目做得好就说好，有问题就指出，不要模糊

## 交付边界

- 只输出分析报告，不修改代码
- 命名问题必须给出 3-7 个候选方案对比，推荐一个最佳方案并说明理由
- 改动量预估：文件数、改动性质（机械替换 vs 逻辑变更）
- 零风险改动（编译期可验）和高风险改动标注区分
